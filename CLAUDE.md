# Voxel Engine — правила проекта

Свой воксельный движок на Rust. Десктоп, одиночная игра, без сети.

Движок — самоцель, а не обвязка вокруг одной игры. Задача — очень оптимизированное
воксельное ядро, на котором потом делается что угодно. Первая нагрузка на него —
игра в духе Minecraft; дальше, вероятно, симуляционная игра («живой мир», искусственная
жизнь) на том же ядре без его переписывания.

Главная цель архитектуры — **сильная расширяемость**: всё, включая собственный контент игры,
подключается как плагины/моды через один и тот же API. Вторая цель — **производительность**.

## Жёсткие ограничения

- Rust stable, edition 2024. Никакого nightly.
- Платформы: Windows (основная), Linux. Разработка ведётся нативно под Windows 11 (без WSL) — см. раздел «Среда разработки».
- Графика: `wgpu` (Vulkan / DX12 / Metal). Без прямого OpenGL.
- Окно и ввод: `winit`. Математика: `glam`. ECS: `bevy_ecs` (только ECS-крейт, НЕ весь Bevy).
- Параллелизм: `rayon` для CPU-задач, каналы `crossbeam-channel` для результатов.
- Сериализация данных: `serde` + `ron` для описаний контента.
- Никаких ассетов, кода или названий Mojang. Текстуры — свои (на старте можно генерировать процедурно).
- Сеть, мультиплеер и браузер (wasm32 target) вне скоупа.

## Архитектура: Cargo workspace

```
crates/
  engine_core/      App, Plugin trait, расписание этапов (stages), события, ресурсы
  engine_registry/  Namespaced ID (`namespace:path`), Registry<T>, заморозка → числовые ID
  engine_world/     Chunk/Section 16³, палитры, координаты, World, трейт WorldGenerator
  engine_worldgen/  Генератор ландшафта на шуме (реализует WorldGenerator)
  engine_mesh/      Greedy meshing, упакованный формат вершины. Чистые функции, без GPU
  engine_render/    wgpu-рендерер, камера, пайплайны, атлас текстур, culling
  engine_platform/  winit, цикл событий, состояние ввода
  engine_assets/    Загрузка RON-описаний контента из папки assets/<namespace>/
  engine_mod_api/   (позже) публичный API для модов; сейчас — только границы и трейты
game_base/          Базовый контент игры, оформленный как плагин с namespace `base`
client/             Бинарник: собирает App из плагинов и запускает
assets/base/        Данные базового контента (blocks/*.ron, textures/)
docs/adr/           Architecture Decision Records
```

Правила зависимостей:
- `engine_mesh`, `engine_world`, `engine_registry` не зависят от `wgpu`/`winit` — их можно тестировать и бенчмаркать headless.
- `engine_render` знает про `engine_mesh`, но не про генерацию мира.
- `game_base` использует только публичный API движка — ровно так же, как будущий мод. Никаких «внутренних» хаков для базового контента.
- Циклических зависимостей между крейтами нет.

## Принципы расширяемости

1. **Всё — плагин.** `trait Plugin { fn build(&self, app: &mut App); }`. Рендер, мир, генерация, базовый контент — плагины. `client` только перечисляет их.
2. **Реестры с текстовыми ID.** Блоки, предметы, генераторы регистрируются как `base:stone`. Числовые ID выдаются при заморозке реестра после загрузки всех плагинов и нигде не хардкодятся.
3. **Data-driven контент.** Свойства блока (текстуры граней, прозрачность, твёрдость, светимость) описываются в RON. Код нужен только для поведения.
4. **События вместо патчинга.** Расширения реагируют на события (`ChunkGenerated`, `BlockChanged`, тик) и не меняют код движка.
5. **Явные этапы кадра/тика** (например `PreUpdate → Update → PostUpdate → Render`), плагины добавляют системы в нужный этап.
6. **Задел под WASM-моды.** Публичные типы мод-API — простые данные (ID, координаты, POD-структуры), без лайфтаймов и трейт-объектов из внутренностей движка, чтобы позже прокинуть их через `wasmtime`.
7. **Симуляция отделена от рендера**: фиксированный тик (20 Hz) для логики мира, рендер с переменным FPS и интерполяцией.
8. **Чанк — не только блоки.** Формат чанка проектируется так, чтобы рядом с массивом блоков
   можно было добавить другие слои данных (освещение, скалярные поля вроде температуры или
   влажности) без изменения API мира. Сами слои сейчас не реализуются — только место под них.
9. **Тик адресуется по регионам, а не глобально.** API обновления мира принимает, *что* тикать,
   а не «тикни всё»: это то, через что потом вводится LOD симуляции. Сейчас реализация
   тривиальная — тикаем всё загруженное.
10. **Сущности — сразу через ECS.** Даже когда сущностей в игре нет, игрок и камера живут
   в `bevy_ecs` как обычные сущности, а не как особый случай в коде движка.

## Производительность

- Чанки: секции 16³, хранение через палитру + bit-packed индексы; однородная секция хранится как одно значение.
- Генерация и мешинг — в пуле `rayon`, главный поток только забирает готовые меши и грузит в GPU с лимитом на кадр.
- Greedy meshing; вершина упакована в 8 байт (позиция в чанке, нормаль, индекс текстуры, AO).
- Минимум draw calls: общий буфер вершин / indirect draw, когда дойдём; frustum culling обязателен с первого этапа.
- В горячих циклах — без аллокаций: переиспользуемые буферы, `Vec::clear()` вместо новых `Vec`.
- Любая оптимизация подтверждается бенчмарком (`criterion`) или замером, а не догадкой.

## Качество кода

- Перед каждым коммитом: `cargo fmt`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`.
- Юнит-тесты обязательны для `engine_registry`, `engine_world` (палитры, координаты), `engine_mesh` (greedy meshing на эталонных случаях).
- `unsafe` — только с комментарием `// SAFETY:` и обоснованием в ADR.
- Ошибки: `thiserror` в библиотеках, `anyhow` только в `client`. Без `unwrap()` вне тестов и явно невозможных случаев (тогда `expect("почему невозможно")`).
- Логирование через `tracing`.
- Значимое архитектурное решение → короткий ADR в `docs/adr/NNNN-название.md`.
- Небольшие коммиты, один логический шаг — один коммит. Формат — Conventional Commits, см. ниже.

## Среда разработки

Разработка и запуск — нативная Windows 11, без WSL. Тулчейн: Rust stable, target
`x86_64-pc-windows-msvc` (нужен MSVC Build Tools / Windows SDK). Оболочка — PowerShell.

- Основной бэкенд графики — DX12, Vulkan как альтернатива. Движок должен уважать
  `WGPU_BACKEND` (dx12/vulkan/gl) и логировать выбранный адаптер.
  В PowerShell переменная задаётся как `$env:WGPU_BACKEND = "dx12"`.
- Пути в коде и скриптах — через `std::path::Path`/`PathBuf`, без хардкода `/` и `\`.
  Файлы в репозитории — UTF-8 без BOM. Нормализация переводов строк для Linux — отложена.
- В README описать сборку и запуск под Windows (PowerShell), требования к драйверам GPU
  и переключение бэкенда. Linux — только как «должно собираться», без отдельных инструкций.
- Headless-крейты (`engine_world`, `engine_mesh`, `engine_registry`) собираются и тестируются
  без GPU и без окна — это требование к архитектуре, а не к ОС.

## Коммиты

Conventional Commits, тема в нижнем регистре, без точки на конце, в повелительном наклонении:

```
<type>(<scope>)!: <что сделано>
```

- `type`: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, `revert`.
- `scope` — имя крейта без префикса `engine_` (`world`, `mesh`, `render`, `registry`, `worldgen`,
  `assets`, `platform`, `core`) либо `base`, `client`, `ci`, `deps`. Необязателен, но желателен.
- `!` или футер `BREAKING CHANGE:` — при изменении публичного API движка или мод-API.
- Замеры производительности в `perf`-коммитах указывать в теле: было → стало.

Примеры: `feat(world): палитра и bit-packing секции`, `perf(mesh): убрать аллокации в greedy-проходе`,
`fix(render): швы на границе чанка при отрицательных координатах`, `feat(mod-api)!: Identifier вместо u16`.

Проверяется в CI (job `Conventional Commits`) для всех коммитов PR, кроме merge-коммитов.

## CI (DevSecOps)

GitHub Actions, два workflow. Красный CI — блокирующий, обходить не нужно: падение чинится, а не глушится.

`.github/workflows/ci.yml` — корректность:
- `Conventional Commits` — формат тем коммитов в PR.
- `Форматирование` — `cargo fmt --all --check`.
- `Clippy` на Windows и Linux — `--workspace --all-targets --all-features -- -D warnings`.
- `Тесты` на Windows и Linux — `cargo test --workspace --all-features`.
- `Release-сборка` под `x86_64-pc-windows-msvc`.
- `Проверка unsafe` — каждый `unsafe {` обязан иметь `// SAFETY:` в пределах 6 строк выше.

`.github/workflows/security.yml` — безопасность (плюс ночной прогон по cron, чтобы ловить
новые CVE в неизменившемся коде):
- `cargo-deny`: `advisories` (уязвимости, заброшенные крейты), `bans` (дубли версий, wildcard-зависимости),
  `licenses` (белый список в `deny.toml`), `sources` (только crates.io).
- `Поиск секретов` — TruffleHog по всей истории.
- `Обзор новых зависимостей` — для PR, порог severity `moderate`.

Dependabot (`.github/dependabot.yml`): cargo — еженедельно, actions — ежемесячно, с темами
коммитов `chore(deps):` / `ci(...)`.

Локально то же самое перед коммитом: `cargo fmt`, `cargo clippy --workspace --all-targets -- -D warnings`,
`cargo test --workspace`, `cargo deny check` (поставить: `cargo install cargo-deny --locked`).

Новая зависимость — отдельный коммит `build(deps):` с одной строкой обоснования: зачем она
и почему нельзя без неё. Лицензия вне белого списка `deny.toml` → не берём.

## Как работать

- Сначала план, потом код. На крупную задачу — покажи план и структуру, дождись подтверждения.
- Не забегай вперёд текущей задачи: задел под будущее — только в виде трейтов/границ, без реализации.
- Если требование противоречит этому файлу — остановись и спроси.
